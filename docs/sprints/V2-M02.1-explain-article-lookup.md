## 1. Bug summary

`complior_explain` does case-insensitive substring matching of the user's query
against `obligation.article_reference`. The tool description tells AI agents
to use `"Art. 50"` form, but production data
(`engine/core/data/regulations/eu-ai-act/obligations.json`) uses the long form
`"Article 50(1)"`. Because `"art. 50"` is not a substring of `"article 50"`,
no match is found.

This affects every short-form article query: `"Art. 4"`, `"Art. 5"`,
`"Art. 27"`, `"Art. 50"`, etc. AI agents that follow the tool description
verbatim get the unhelpful response `'No obligation found matching "Art. 50".
Try: "Art. 50", "OBL-001", or a keyword.'` — which is doubly misleading
because the suggested example "Art. 50" is itself the failing input.

This is a **v1.0 bug** — `complior_explain` is part of the legacy 7 tools
shipped in v1.0.0. V2-M02 did not introduce it, only surfaced it via the
live E2E run on 2026-05-08.

---

## 2. Fix specification

The handler in `engine/core/src/mcp/handlers.ts` (around line 144–173) must
normalize Art./Article forms in **both directions**, so the query matches
the data regardless of which form either uses.

**Acceptance:**

| Query form | Must match data |
|------------|-----------------|
| `"Art. 50"` | `"Article 50"`, `"Article 50(1)"`, `"Article 50(2)"`, `"Art. 50"` |
| `"Article 50"` | same set |
| `"Art.50"` (no space) | same set |
| `"art 50"` (lowercase, no period) | same set |
| `"OBL-014"` | `obligation_id: "eu-ai-act-OBL-014"` (regression) |
| `"Literacy"` | `title: "AI Literacy"` (regression — keyword in title) |
| `"Article 999"` | no match → graceful error string (regression) |

**Determinism:** `complior_explain({article: "Art. 27"})` and
`complior_explain({article: "Article 27"})` must produce **byte-identical**
output (same JSON, same order).

---

## 3. Suggested implementation (for nodejs-dev)

The fix is small — likely 4–6 lines in `complior_explain` handler. Possible
approach: extract the article number from the query and match it against
both `"Art. <n>"` and `"Article <n>"` forms in the data.

```typescript
// Pseudo-code — exact wording is dev's call
const normalize = (s: string): string =>
  s.toLowerCase()
    .replace(/^\s*art(?:\.|icle)?\s*/i, 'article ')  // canonical form
    .trim();

const queryCanonical = normalize(args.article);
const matches = data.obligations.obligations.filter((o: Obligation) =>
  o.obligation_id.toLowerCase().includes(args.article.toLowerCase()) ||
  normalize(o.article_reference).includes(queryCanonical) ||
  o.title.toLowerCase().includes(args.article.toLowerCase()),
);
```

The exact regex / normalization helper is dev's choice — tests are the spec.

**Architecture requirements:**

- ✅ Pure function inside the handler closure (no global state, no side effects)
- ✅ Reuse existing `Obligation` type from `data/schemas/schemas.js`
- ✅ No new dependencies; standard string ops only
- ✅ Handler signature unchanged (zero breaking change)
- ✅ Error string format unchanged for unknown articles
