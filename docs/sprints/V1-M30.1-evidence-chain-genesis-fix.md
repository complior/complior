## 2. Root cause (W-1)

`engine/core/src/domain/scanner/evidence-store.ts`:

```ts
const MAX_ENTRIES = 1000;
// …
const trimmedEntries = newEntries.length > MAX_ENTRIES
  ? newEntries.slice(newEntries.length - MAX_ENTRIES)  // ← drops genesis!
  : newEntries;
```

`verify()` walks the chain expecting `entries[0].chainPrev === null` (genesis property). After eval (~1000+ findings) trims, the new `entries[0]` has `chainPrev = <hash of pruned genesis>`. Verify reports "broken chain link" → scan-service adds `criticalCap: "Evidence chain missing or invalid"` → report renders "Score capped" warning.

V1-M30 W-1 integration test passed because it only does `init` + `scan` (chain stays at ~10 entries, no trim). The /deep-e2e flow does `init → scan → eval → fix → report`, where `eval` blows past 1000 entries.

## 4. Architecture Requirements (W-1.1)

The trim logic in `evidence-store.ts` MUST:

```ts
// PRESERVE genesis at entries[0], trim from index 1 onwards
if (newEntries.length > MAX_ENTRIES) {
  const genesis = newEntries[0];
  const tail = newEntries.slice(newEntries.length - (MAX_ENTRIES - 1));
  // tail[0].chainPrev links to genesis.hash → still valid
  // BUT verify() now sees: genesis (chainPrev=null) → tail[0] (chainPrev=tail0_prev_hash)
  // → broken if tail[0].chainPrev !== genesis.hash
}
```

Two acceptable implementations:

**Option A (preferred — preserves cryptographic chain integrity):**
- Keep `entries[0]` (genesis with `chainPrev=null`).
- Skip middle entries — keep last `(MAX_ENTRIES - 1)` from tail.
- Update `verify()` to recognise that a single "trim gap" between entries[0] and entries[1] is allowed: when verifying entries[1], `expectedPrev` may be `entries[0].hash` OR `entries[1].chainPrev` (i.e. accept the recorded predecessor).

**Option B (simpler — bump cap):**
- Raise `MAX_ENTRIES` to e.g. 100_000 to cover normal eval workloads.
- Document that very-long-running engines will eventually hit the same bug.
- DO NOT take this option — it just delays the failure.

**Mandatory: Option A.** Fix it correctly so the chain stays valid no matter how long it runs.

### Architectural checklist for the dev:
- [ ] `Object.freeze` applied to the trimmed `entries` array and any new entry pushed
- [ ] `verify()` is a pure function — same chain in → same `{valid, brokenAt, issues}` out
- [ ] No new error types unless documented in `evidence-store.ts` JSDoc
- [ ] Any new helper exported from `evidence-store.ts` with a JSDoc and ≥1 test
- [ ] Does NOT touch `init-service.ts` (the genesis is the same; only trim/verify changes)
- [ ] Does NOT raise `MAX_ENTRIES` — fix the algorithm, not the threshold
