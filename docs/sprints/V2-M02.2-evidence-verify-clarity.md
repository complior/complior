## 1. Bug summary

`complior_evidence_verify` returns `valid: true` while `issues: ["Entry N: signature mismatch — entry signed by a different key (or tampered)"]` for every entry. The output looks self-contradictory — "valid" says OK, "issues" says tampering.

Root cause is **by design** in `engine/core/src/domain/scanner/evidence-store.ts:232-243`:

> _Signature mismatches are a SOFT failure. They are recorded in `issues` for audit, but they do NOT flip `valid` to false. Rationale: the chain may legitimately contain entries signed by different keys over its lifetime (e.g. key rotation, project-scoped HMAC genesis vs composition-root ed25519 entries). A chain whose hashes link correctly is "structurally intact" — the report cap "Evidence chain missing or invalid" exists to surface structural problems (gaps, broken links, missing genesis), not signature mismatches against the current verifier's key._

So the **store semantics are correct** — but the **handler output shape** dumps two distinct concerns under the same `valid`/`issues` fields, making the contradiction confusing for AI agents.

This is V2-M02 caused (new tool, new surface) — it didn't exist before V2-M02 because there was no MCP path to `verify()` output.

---

## 2. Fix specification

Update only `complior_evidence_verify` handler in `engine/core/src/mcp/handlers.ts` (around lines 415–443). Partition `verifyResult.issues` into two arrays by pattern, then expose four explicit fields plus a human-readable summary. **Keep `valid` and `issues` fields for backward compatibility** with v1.1.0 early adopters.

### Output shape (after fix)

```jsonc
{
  // Backward-compat fields (kept as aliases)
  "valid": true,                  // ≡ structurallyValid
  "issues": [...],                // all messages combined (structural + signature)
  "brokenAt": undefined,          // unchanged

  // New explicit fields
  "structurallyValid": true,      // chain hashes link, no gaps, no content tampering
  "signaturesIntact": false,      // every non-genesis signature verifies against current key
  "structuralIssues": [],         // broken-link / hash-mismatch / missing-genesis messages
  "signatureIssues": [            // soft warnings — key rotation / HMAC vs ed25519
    "Entry 0: signature mismatch — entry signed by a different key (or tampered)"
  ],
  "summary": "Chain structurally valid (12 entries, 3 scans). 12 signature warnings — signed by different keys (key rotation or session change, not tampering).",

  // Summary fields (unchanged)
  "totalEntries": 12,
  "scanCount": 3,
  "firstEntry": "2026-04-01T00:00:00Z",
  "lastEntry": "2026-05-07T00:00:00Z"
}
```

### Partition rule

A message in `verifyResult.issues` is a **signature issue** if it matches case-insensitive `signature mismatch`. Otherwise it is a **structural issue**. This is a pure string operation — no evidence-store changes required.

### Summary string composition

| Condition | Summary text |
|-----------|--------------|
| Healthy chain (both intact) | `"Chain structurally valid (<N> entries, <S> scans). All signatures verified."` |
| Key rotation only (Bug-2 case) | `"Chain structurally valid (<N> entries, <S> scans). <K> signature warnings — signed by different keys (key rotation or session change, not tampering)."` |
| Structural failure | `"Chain BROKEN at entry <brokenAt>: <first structural issue message>."` |
| Empty chain | `"Empty evidence chain (no scans recorded yet)."` |
